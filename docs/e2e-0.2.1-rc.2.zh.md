# E2E 验证记录：dsh 0.2.1-rc.2 真机（2026-10-19）

> 0.2.0-rc.2 → **0.2.1-rc.2**（npm `next` 标签，2026-10-17 发布）迁移的真机验证。
> 本轮不是零改动：冷恢复路径按 0.2.x 的 `sessionController` 契约重写（旧实现调用的 `page` 形状从一开始就不匹配），
> `session_search` 补取消信号，可选服务查找在 HMR 窗口不再抛错。零 token 相与两次真实 turn 全绿。

## 环境

-   宿主：`@deepseek-ai/dsh@0.2.1-rc.2`（临时前缀安装，非全局）
-   **隔离 home**：`DSH_HOME` 指向临时目录；复制入 `.credentials.yaml`（DeepSeek 账号登录）与
    `settings.yaml`（取自本机 `settings.yaml.imported`，首启导入后宿主又改回 `.imported`）。
    导入会把旧设置整层写进 profile patch——默认模型被改成 pi-ai 的条目、`session-query-sqlite` 被关成
    `:memory:`/`openAt: never`，所以 e2e profile 的 patch 显式覆盖 `agent-default-model`
    （`deepseek-account/deepseek-flash`）与 `session-query-sqlite`（文件路径 + `openAt: startup`）
-   profile：`--profile carrot-e2e --from-default-profile web`，插件经
    `dsh plugin --profile carrot-e2e add link:<仓库>` 装成 link（CLI 自动把包名加入 `dsh.profile.bundles`）；
    MCP 端口让到 8095（避开常驻实例 8090 与 smoke 套件占用的 8091/8099）
-   无人值守：`DSH_PERMISSION_MODE=danger-full-access`（审批策略 `never`、沙箱全开）；
    `ask` 策略下 pwsh 工具会停在审批上，客户端超时也拿不到 turn 收场
-   客户端：`test/e2e.ts`（重写为会话中心工具面，`E2E_SESSION_ID` 指定续接目标）

## 迁移点核对（0.2.0-rc.2 → 0.2.1-rc.2）

-   **类型面**：`dsh-agent` / `dsh-llm` / `dsh-session` / `dsh-tools` / `dsh-agent-preset-registry`
    对上轮源码的改动是加法（新增 image 目标、plugin record、PTC 事件 meta、preset 检查接口），
    `npm run build` 零报错；`ToolPresentationMode` 去掉 `both`、preset registry 删掉
    `serviceForAgent` / `standingMountFor` / `livePresetMounts`——本插件都没用
-   **Session 格式**：`SESSION_FORMAT_VERSION` 仍为 4；新增 `formatStatus: 'migration-required'`
    与 `session/migration-required` 错误（旧格式会话需先由界面打开完成迁移）。本插件现在把
    `resolveAgent` / `inspect` 的宿主错误原样透出，不再是误导性的"只支持 live"
-   **sessionController**：`page` 在 0.2.0 就已是 `{ address, throughSeq }` → `{ records }`（旧代码的
    `{ sessionId }` → `.events` 从未成立）；`inspect(sessionId)` 返回
    `{ meta, inheritedEventCount, events }`；`resolveAgent(sessionId)` 是界面打开旧会话的官方冷恢复；
    `search(request, signal)` 的 signal 是必需参数；`fork` 的子会话 id 改为 `session-<uuid>`
-   **client 契约**：`window.__ModuleLoader__.load({ id, factory })` 静态 bundle 协议未变；
    `settings.section` 仍是 `id/order/label`（label 支持 thunk），面板在真机照常渲染
-   **manifest**：`dsh.client.platform/inject` 未变；`engines.dsh` 在 0.2.1 会被 Plugin Manager /
    启动期真实执行，本插件现在声明 `>=0.2.1-rc.2`

## 发现与处置

1.  **冷恢复实际不可用（本轮修复）**：旧实现调 `sessionController.page({ sessionId })` 再读 `.events`，
       宿主两个版本都要求 `{ address: { kind:'session', sessionId }, throughSeq }` 且返回 `records`，
       异常被吞掉后统一报 "cannot determine the model of persisted session"。改为
       `sessionController.resolveAgent(sessionId)`（界面同源：恢复模型选择、组装 preset、处理迁移），
       冒烟桩同步成 0.2.1 的 `inspect` / `resolveAgent` 形状，真机重启后续接通过。
2.  **`session_search` 缺取消信号**：0.2.x 的 Remote `search(request, signal)` 在入口直接
       `signal.throwIfAborted()`，缺参报 `Cannot read properties of undefined`。改为透传工具调用的
       `extra.signal`，冒烟新增"必须带信号"断言。
3.  **HMR 重载窗口的服务空窗**：运行中改 profile patch 触发重组时，`sessionController` /
    `agentPresets` 短暂不可用；本插件 `serviceOf` 的属性回退在真机对未 inject 的服务直接抛
    `cannot get property ... without inject`，把 `session_search` / `session_fork` 打崩。
    改为两条查找路径都兜错、返回 `undefined`（可选依赖缺席 = 功能报不可用，不崩调用）。
    干净重启后服务恢复；该 profile 的 `session-query-sqlite` 若保持 `openAt: never`，
    `session_search` 会如实返回宿主"检索索引已关闭"的错误（部署配置，不是插件缺陷）。
4.  **桌面壳的 origin 兼容（真机面板回归发现）**：0.2.1 桌面客户端用 `dsh-app://` 自定义 scheme
    承载页面，且其 scheme 处理器转发请求时丢掉了 `Origin` 与 `Sec-Fetch-*`——真机 403 回包是
    `site=-, origin=-, host=127.0.0.1:64223`，面板所有写操作被拒（读操作不校验，故能显示数据却
    改不了任何东西）。改为：`Sec-Fetch-Site` 为 same-origin 放行、cross-site 拒绝；`dsh-app:`
    origin 直接放行；两个头都缺时只接受回环 Host 的本机客户端（浏览器跨站写请求必带 Origin，
    且 JSON 还要过 CORS 预检）；其余按 Origin/Host 比对并兼容同端口回环别名。该修复在运行中的
    桌面实例上经一次配置写入触发的插件重载验证：同形状请求由 403 变为通过门禁。
5.  **工作区挂载警告（一次性）**：首轮未干净退出的实例上出现过一次
    `domain 'workspace' table 'workspaces' has no record ... to update`；随后 4 次干净新建均无复现，
    `workspace.json` 里会话已正确挂到工作区。判定为中断进程留下的组合状态，未改代码。
